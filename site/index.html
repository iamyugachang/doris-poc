FE 掛了、BE 掛了、整台 VM 掛了，client 還能寫嗎？

三台 VM 各跑一個 FE 與一個 BE，client 每秒對同一把 key 做 INSERT → UPSERT → SELECT → DELETE → SELECT，同時用 mysql / jdbc / arrow-flight 三種協定。我們把 16 種故障各注入三輪，量 client 中斷幾秒、寫入還能不能成功、資料有沒有不一致。

TAKEAWAYS結論

  • 單一故障（12 格）：11 格讀寫正常，1 格不是（master FE hang（kill -STOP））。mysql 中斷最長 137s（master FE hang（kill -STOP））。
  • 雙重故障（4 格）：VM 停 + 另一台 FE dead→不可用（flight 讀取失敗）；VM 停 + 另一台 BE dead→只讀（flight 讀取正常）；兩台 VM 停→不可用（flight 讀取卡住）；交錯故障→不可用（flight 讀取失敗）。等級由 FE 與 BE 各自的多數決決定：任一層剩 1/3，寫入就停。
  • 資料一致性：48 次執行、26,438 次操作，SELECT 驗證不一致 0 次。寫入在中斷視窗內失敗會換新 key 重來，不留下半套資料。
  • 恢復：restore 到 3 FE / 3 BE 全 alive、12 副本 OK，4～266 秒（含 VM 開機），不需人工介入。
  • Arrow Flight SQL：Doris 4.1.1 只走查詢，INSERT/DELETE 回 getMysqlChannel not in mysql connection；寫入請用 MySQL 協定或 Stream Load。
  • client 端建議：JDBC 多主機 URL 最省事；自行實作時逾時設 2～3 秒、失敗重連時輪替主機，避免卡在轉發給已死 master 的 follower 上。

ARCHITECTURE正常狀態 vs 掛掉一台

3 個 FE 都是 FOLLOWER，以多數決選出 1 個 master；3 個 BE 是一個資料池，每個 tablet 三副本各放一個 zone。client 帶三台 FE 的主機清單，第一台連不上就試下一台。

三個 client 同時觀察 VM 停機，第 1 輪，mysql client 視角。橘/綠帶是 client 受影響的區間。
